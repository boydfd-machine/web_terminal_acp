# Agent Trace Graph

把本次任务的执行过程,从"线性日志"重新解读成一张**带分叉、有成败着色的意图树**,输出为一个**单文件可交互 HTML**(点节点看该步详情)。

核心分工:**你(agent)只产出一份 JSON**,描述走过的路径;**渲染脚本负责生成全部图形(手工排版的纯 SVG)和 HTML**。你绝不手写任何图形语法。你只要保证 JSON 合法。

渲染采用**离线纯 SVG**(无 mermaid、无 CDN 依赖):**从上往下的树状布局**——布局形状完全由 `edges` 的拓扑决定(不是按 step 摞成一列)。失败的尝试是从某个节点**岔出去的死枝**(到此为止,不再往下);流程"回到"的那个节点会**长出新的兄弟分支** 继续走。卡片式节点、连边带圆角、状态着色。交互:**悬停节点或连线**会高亮相关路径并让虚线流动、其余淡出;**点击节点**弹出详情面板。

## 何时用

- 用户想看"agent 为了做某事走了哪些路、哪条撞墙、哪条走通"。
- 任务复盘 / 演示 / 交接时,需要一张比日志更直观的过程图。
- 一次任务做了多件事,想分别看每件事的成败路径(→ 多条绿色终点)。

## ⭐ 核心:这是一棵树,不是一条直线

**最容易犯的错误是把所有节点按时间顺序串成一条直线。** 真实的 agent 工作几乎总是树状的:试一条路、撞墙、回到之前某个节点、换一条路再试。你必须把这个"分叉"如实画出来。

布局形状**完全由 `edges` 决定**(渲染器按边做树状分层),与 step 数字无关。所以构图的关键全在边怎么连:

```
            #1 定位问题  ← 决策/分叉点
           ╱           ╲
   (灰)#2假设A          (绿)#5假设B   ← 两条兄弟分支,从同一个父节点 #1 岔出
      │                   │
   #3 尝试               #6 修复
      │                   │
  (红)#4 撞墙 ✗         ✅ 走通        ← 死枝到此为止,绝不再往下接
      ╎
      ╰╴↩ backtrack 回到 #1            ← 紫色虚线:标注"实际回到了哪个节点"
```

**三条铁律**:

1. **失败节点是叶子**:`status:deadend` 的节点不能再有 `tried`/`leads-to` 边从它出发。撞墙了就停在那里。
2. **重试是兄弟,不是后继**:agent 撞墙后回到节点 X 再换条路,那么新路第一个节点的 `tried` 边要**从 X 出发**(`{"from":"X", ...}`),而不是从失败节点出发。这样新路成为 X 的另一个子分支。
3. **回溯单独用 `backtrack` 边标注**:从失败节点画一条 `kind:"backtrack"` 边指向**它实际回到的那个节点**。这条边只是注解(紫色虚线 ↩),不影响树形。**回到的节点可能是直接上游,也可能是好几步之前的更早节点**——如实指向真正回到的那个。

> 一个目标里出现 N 次"试错→回退→换路",树上就应有 N 个红色/黄色死枝从对应的分叉点岔出。如果你画出来是一条直线没有任何分叉,几乎可以肯定是漏掉了试错过程——回去补。

## 工作流程

### 1. 回忆本次任务的真实路径

凭你自己的上下文(你最清楚自己试过什么),把执行过程拆解成意图树。做四个判断:

1. **切段**:把连续的工具调用归并成一个个"尝试/路径"——一段朝同一假设连贯努力的动作。不要一个工具调用一个节点,要按"意图"聚合。
2. **归类到目标**:任务可能有多件事(多个 `goal`),每个尝试挂到对应目标下。每个目标最终应有一个 `goal` 类型的绿色终点。
3. **判定成败 + 找分叉点**:每段是 `success`(走通)/ `deadend`(碰壁)/ `partial`(部分)/ `neutral`(中间)。**碰壁后,问自己:我当时回到了哪个节点重新出发?** 那个节点就是分叉点,新尝试要从它接出去(见上面铁律 2)。
4. **连边建树**:`tried`/`leads-to` 边搭出树的父子关系;失败节点用 `backtrack` 边指回它实际返回的那个祖先节点。

**保真原则**:如实反映试错——撞墙就标红、岔成死枝并写清原因,不要美化成一条直线;部分有效的尝试标 `partial`(黄)。

### 2. 产出 JSON

按下面的 schema 写(这个例子**就是一棵带分叉的树**:`#1` 岔出失败的签名分支和成功的 DB 分支)。把它写到临时文件,例如 `/tmp/agent-trace.json`:

```json
{
  "task": "修复支付回调 500",
  "goals": [
    { "id": "g1", "label": "目标: 修复支付回调" }
  ],
  "nodes": [
    { "id": "a1", "type": "decision", "label": "定位: 回调返回 500", "goal": "g1", "step": 1, "status": "neutral", "detail": "从错误日志入手。这是后续所有分支的共同分叉点。" },

    { "id": "a2", "type": "decision", "label": "假设A: 签名校验失败", "goal": "g1", "step": 2, "status": "neutral", "detail": "怀疑第三方签名验不过。" },
    { "id": "a3", "type": "action", "label": "🔧 改签名算法 sha256", "goal": "g1", "step": 3, "status": "deadend", "detail": "签名对上了但仍 500。走了两步,死路。判定签名不是根因,回到 #1 重新定位。" },

    { "id": "a4", "type": "decision", "label": "假设B: DB 写入超时", "goal": "g1", "step": 4, "status": "neutral", "detail": "回到 #1 换方向,看堆栈其实是 DB 超时。" },
    { "id": "a5", "type": "action", "label": "🔧 加订单表索引", "goal": "g1", "step": 5, "status": "success", "detail": "全表扫描超时,加索引后回调 200。" },
    { "id": "g1ok", "type": "goal", "label": "✅ 回调修复", "goal": "g1", "status": "success", "detail": "压测 1000 并发全 200。" }
  ],
  "edges": [
    { "from": "a1", "to": "a2", "kind": "tried", "status": "neutral", "label": "先查签名" },
    { "from": "a2", "to": "a3", "kind": "tried", "status": "neutral", "label": "" },
    { "from": "a3", "to": "a1", "kind": "backtrack", "status": "neutral", "label": "签名非根因,回到 #1" },

    { "from": "a1", "to": "a4", "kind": "tried", "status": "success", "label": "换查 DB" },
    { "from": "a4", "to": "a5", "kind": "tried", "status": "success", "label": "命中超时" },
    { "from": "a5", "to": "g1ok", "kind": "leads-to", "status": "success", "label": "压测通过" }
  ]
}
```

注意这个例子里的树形信号:
- `a1` 有**两条** `tried` 出边(→`a2` 失败枝、→`a4` 成功枝),所以它是分叉点。
- 失败枝末端 `a3` **没有** `tried` 出边(它是叶子),只有一条 `backtrack` 边指回 `a1`。
- 成功的新尝试 `a4` 的 `tried` 边**从 `a1` 出发**,不是从 `a3` 出发——这就是"重试是兄弟不是后继"。
- 若回到的是更早的节点(比如回到 3 步前),`backtrack` 和新分支的 `from` 就指向那个更早的节点,树会从那里岔开。

字段要点:
- `nodes[].type`:`decision`(假设/决策,菱形,通常是分叉点)/ `action`(操作,矩形,加 🔧 emoji 更醒目)/ `goal`(目标终点,圆角)。
- `nodes[].status` / `edges[].status`:`success`=绿,`deadend`/`failed`=红,`partial`=黄,`neutral`=灰。
- `edges[].kind`:`tried`/`leads-to` 搭树(决定布局);`backtrack` 只做注解(紫色虚线 ↩),不影响树形。
- `step`:真实执行序号,只用于卡片上的徽章和阅读顺序,**不决定布局**。
- 根节点(总任务)由脚本自动生成,连到所有"无树父节点"的起始节点,不要自己写根。
- **每个目标至少要有一个 `success` 节点**,否则没有绿色终点(脚本会告警)。
- 一个节点若被两条 `tried` 边指向(罕见,如多路汇合),第二条会画成灰色虚线注解,不破坏树形。

### 3. 渲染成 HTML

```bash
python3 scripts/render.py /tmp/agent-trace.json -o /tmp/agent-trace.html
```

脚本会:校验 JSON(重复 id / 悬空边 / 无绿色终点都会报错或告警)→ 按 edges 做树状分层布局 → 输出自带 SVG 的单文件 HTML(离线可开,无任何外部依赖)。

### 4. 交付

告诉用户 HTML 路径,并简述这张图:有几条目标分支、哪几条碰了壁(原因)、每次回退到了哪个节点、最终走通的路径。提示用户用浏览器打开该 HTML 查看(可悬停高亮、点节点看详情)。**不要截图**——直接给路径即可。

## 视觉约定速查

| 维度 | 编码 |
|---|---|
| 布局 | 从上到下的树;根任务在顶,每个目标一棵子树,分叉=试了多条路 |
| 节点形状 | 菱形=decision,矩形=action,圆角=goal |
| 颜色 | 绿=走通,红=碰壁,黄=部分,灰=中间,蓝=根任务 |
| 树边 | 绿粗实线=走通,红虚线=失败(边上写原因),灰线=中间步骤 |
| 回溯边 | 紫虚线 ↩,从失败死枝指回"实际回到的那个节点"(可跨多步) |
| 死枝 | 失败/部分尝试岔出后到此为止,不再往下接 |
| 序号徽章 | `#n` = 真实执行顺序,树状图也能读出先后 |

## 注意

- **不要截图**:渲染完直接把 HTML 路径交给用户,让他自己用浏览器打开。不要用 google-chrome / headless 截图——既慢又费 token,没有必要。
- 这是**复盘可视化**,不是日志转储。聚合到"意图"粒度,一张图能一眼看懂胜过 50 个琐碎节点。
- **务必画成树,别画成直线**:有试错就有分叉。一条没有任何红/黄死枝的直线,往往是漏掉了碰壁过程。
- 多件事 = 多个 `goal` + 多棵子树,各有自己的绿色终点。
- 如实标红碰壁死枝、并用 `backtrack` 标清回到了哪个节点——试错与回退恰恰是这张图最有价值的部分。
